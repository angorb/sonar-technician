# CLAUDE.md — sonar-technician

Windows tray utility in Rust that drives SteelSeries GG Sonar's **undocumented local HTTP API**. It provides 1% volume steps, channel-select hotkeys, output-device switching, support for Classic and Streamer mode, and a click-through overlay. The full spec is in `REQUIREMENTS.md`. Read it before starting larger changes.

## Commands

```powershell
cargo build                     # debug build (console window visible, handy for logs)
cargo build --release           # release build (no console; windows_subsystem = "windows")
cargo run -- probe              # discover Sonar and dump every GET endpoint to ./probe-<UTC timestamp>/
cargo run -- set game 42        # CLI: set a channel's volume without hotkeys
cargo test                      # unit tests (controller + parsing; no Sonar needed)
cargo clippy --all-targets -- -D warnings
cargo fmt
```

- Target: `x86_64-pc-windows-msvc`, stable Rust.
- Use debug builds (`cargo run -- ...`) for CLI commands for now: release builds use the `windows` subsystem and have no console attached, so CLI output is lost until `AttachConsole` is added in Phase 3.
- Tests must pass **without** Sonar running. Tests that hit a real Sonar are `#[ignore]` and are run manually with `cargo test -- --ignored`.

## Layout

```
src/
  main.rs          # arg parsing: tray app (default) | probe | set | ...
  config.rs        # TOML config: load/validate/defaults/hot-reload
  controller.rs    # pure state machine: mode, active (mix, channel), volumes, devices, coalescing
  actions.rs       # Action enum (volume_up, next_channel, next_output_device, ...)
  sonar/
    mod.rs         # SonarApi trait + types
    discovery.rs   # coreProps.json -> /subApps -> webServerAddress
    client.rs      # HTTP impl of SonarApi, retry-once-after-rediscovery
    routes.rs      # EVERY route string lives here, nowhere else
  probe.rs         # `probe` subcommand
    models.rs      # serde types built from docs/api-samples/*.json
  platform/
    hotkeys.rs     # RegisterHotKey, chord parsing (F13–F24 + modifiers)
    overlay.rs     # layered, topmost, click-through, no-activate window
    tray.rs
    autostart.rs   # HKCU\...\Run
    single_instance.rs
    endpoint_volume.rs  # optional Core Audio writer for Sonar virtual devices
docs/api-samples/  # raw JSON captured by `probe`: the source of truth for models.rs
```

## Architecture rules

- **The UI thread never blocks.** The Win32 message loop handles hotkeys, the tray and the overlay only. All HTTP goes through a worker thread connected by channels.
- **Latest-wins writes.** Keep a pending write slot per target `(mix, channel)`, with at most one request in flight per target, and send the newest value when the request completes. The overlay shows the *local* value immediately. It doesn't wait for Sonar.
- **The controller is pure.** `controller.rs` has no Win32 or HTTP imports. It takes `Action`s and `SonarEvent`s and emits commands and UI snapshots. Unit-test it heavily against a fake `SonarApi`.
- **Sonar is the source of truth.** Re-read volumes on startup, on channel switch and after about 3 s idle, so changes made in the Sonar UI aren't overwritten by stale cached values.
- Degrade per feature. If one endpoint breaks after a GG update, only that action fails, with an overlay message plus a log entry (URL, status, body excerpt).

## Sonar API notes (unofficial, can change with any GG update)

Discovery:
1. Read `coreProps.json`: `%ProgramData%\SteelSeries\GG\coreProps.json`, falling back to `%ProgramData%\SteelSeries\SteelSeries Engine 3\coreProps.json`. Use the key `ggEncryptedAddress`.
2. `GET https://{ggEncryptedAddress}/subApps`. The certificate is self-signed and regenerated by GG, so skip verification **for this loopback request only**.
3. The base URL is `subApps.sonar.metadata.webServerAddress` (plain `http://127.0.0.1:<random port>`). Check `isEnabled`/`isReady`/`isRunning`.
4. The port changes every GG launch. On a transport error, rediscover and retry once.

Known routes. **Confirmed** = seen working on the user's machine (GG version noted); ✅ = multiple community sources agree but not yet exercised here; ⚠️ = unverified or conflicting.

| Purpose | Route | Status |
|---|---|---|
| Mode | `GET /mode/` returns `"classic"` or `"stream"` | **Confirmed** GG 124.0.0 |
| Set mode | `PUT /mode/{classic\|stream}` (no body) | ✅ |
| Volumes (Classic) | `GET /volumeSettings/classic` | **Confirmed** GG 124.0.0 (shape below) |
| Volumes (Streamer) | `GET /volumeSettings/streamer` | **Confirmed** GG 124.0.0 (shape below) |
| Set volume (Classic) | `PUT /volumeSettings/classic/{channel}/Volume/{0.00-1.00}` | ✅ (master casing ⚠️: `master` vs `Master`) |
| Mute (Classic) | `PUT /volumeSettings/classic/{channel}/Mute/{true\|false}` | ✅ |
| Set volume (Streamer) | `PUT /volumeSettings/streamer/{streaming\|monitoring}/{channel}/volume/{v}` | ⚠️ casing of `volume` |
| Mute (Streamer) | `PUT /volumeSettings/streamer/{slider}/{channel}/isMuted/{bool}` | ⚠️ |
| Devices | `GET /audioDevices` | **Confirmed** GG 124.0.0 (shape below) |
| Device per channel (Classic) | `GET /classicRedirections` (list); `PUT /classicRedirections/{game\|chat\|media\|aux\|mic}/deviceId/{id}` | GET **Confirmed** GG 124.0.0; PUT ✅ |
| Streamer redirections | `GET /streamRedirections`; `GET /streamRedirections/isStreamMonitoringEnabled` (bare `true`/`false`) | GET **Confirmed** GG 124.0.0; ⚠️ PUT route for changing device |
| Streamer mix routing | `PUT /streamRedirections/streaming/redirections/{channel}/isEnabled/{bool}` | ⚠️ |
| ChatMix | `GET /v1/chatMix` → `{"balance":0.44,"state":"enabled","id":"…"}`. `/chatMix` is **404** on GG 124. PUT `?balance=` ⚠️ | GET **Confirmed** GG 124.0.0 |
| Presets | `GET /configs` (~1.4 MB, 400+ presets), `GET /configs/selected` (list, one per `virtualAudioDevice`), `PUT /configs/{id}/select` | GETs **Confirmed** GG 124.0.0 (out of scope for v1) |

Response shapes (GG 124.0.0; raw samples in `docs/api-samples/{classic,stream}/`):
- **`/volumeSettings/*`**: `{"masters": {"classic": {volume, muted}, "stream": {"streaming": {volume, muted}, "monitoring": {volume, muted}}}, "devices": {"<game|chatRender|chatCapture|media|aux>": {"classic": {…}, "stream": {…}}}}`. Volumes are floats like `0.71249974`, not 2-decimal. The mute field is `muted` in GET responses. `/classic` fills only the `classic` halves (`stream` is `{}`), and `/streamer` fills only the `stream` halves (`classic` is placeholder `0.0`). Both return 200 in either mode, **but `/volumeSettings/classic` returns placeholder `1.0` for every channel (not master) while in Streamer mode.** Only trust the endpoint that matches the current mode.
- **`/audioDevices`**: a list of `{friendlyName, id, dataFlow: "render"|"capture", role, channels, defaultRole, fwUpdateRequired, state: "active", isVad}`. For Sonar virtual devices (`isVad: true`), `role` is the volume token (`game`, `chatRender`, `media`, `aux`, `chatCapture`, plus `stream` in Streamer mode); for real devices it's `"none"`. **Use `role` to find a channel's virtual device for the Core Audio path.** Don't match on the friendly name. Streamer mode adds "SteelSeries Sonar - Stream" render and capture devices. Output candidates are `!isVad && dataFlow == "render"`; mic candidates are `!isVad && dataFlow == "capture"`.
- **`/classicRedirections`**: a list of `{id: "game"|"chat"|"media"|"aux"|"mic", deviceId, isRunning}`. `isRunning` is `false` in Streamer mode.
- **`/streamRedirections`**: a list of `{streamRedirectionId: "streaming"|"monitoring"|"mic", deviceId, status: [{role: <volume token>, isEnabled}], isRunning}`. There is one device per mix, not per channel. `status` is the per-channel mix routing, and it's empty for `mic`.
- **Device IDs** look like `{0.0.0.00000000}.{guid}` (render) or `{0.0.1.00000000}.{guid}` (capture). ⚠️ Unverified whether PUT paths need `{`/`}` percent-encoded.

Channel tokens differ by route:
- Volume routes and `/audioDevices` `role`, `/streamRedirections` `status.role`: `master`, `game`, `chatRender`, `media`, `aux`, `chatCapture`
- Redirection routes: `game`, `chat`, `media`, `aux`, `mic`

Keep this mapping in `routes.rs`.

Quirks to respect:
- Round volumes to **2 decimals** before putting them in the URL. Reject NaN.
- Sonar **ignores a write equal to its stored value**. To force a re-apply, send ±0.01 and then the real value.
- A **device switch rebuilds the audio path**, and volume/mute writes during it are dropped. Re-apply after about 400 ms and again after about 1.5 s.
- Error text `Cannot be called in current mode` means the cached mode is stale. Refresh the mode and retry once.
- REST channel writes may change the audio without updating the GG UI. Workaround for Classic channels: set the **Windows endpoint volume** of Sonar's virtual device ("SteelSeries Sonar - Gaming / - Chat / - Media / - Aux / - Microphone"). Sonar mirrors it into its fader and pushes it to GG. Note the names don't match the route tokens ("Gaming" ≠ `game`). `master` has no virtual device and always goes through REST. Changing master can make GG rescale how the other channels are displayed.
- Virtual device IDs change when GG rebuilds its driver. Match devices by ID first and by name as a fallback.

**When a route or shape is confirmed or changed, update this table and `docs/api-samples/` in the same commit.**

## Platform notes

- Use `RegisterHotKey` for global hotkeys (F13–F24 are VK_F13..VK_F24, 0x7C–0x87). Don't install a low-level hook unless testing proves `RegisterHotKey` misses events.
- Overlay window styles: `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`. Show it with `SW_SHOWNOACTIVATE`. It must never take focus. Make it per-monitor DPI aware (manifest or `SetProcessDpiAwarenessContext`).
- The overlay can't draw over exclusive-fullscreen games. That's expected, so document it rather than fight it.
- Config goes in `%APPDATA%\sonar-technician\config.toml` and logs in `%LOCALAPPDATA%\sonar-technician\logs`.
- Only talk to loopback. Never disable TLS verification globally. Use a dedicated client for the discovery call.

## Environment
- **Dev:** Windows 11 desktop, repo inside WSL2 Debian (`~/projects/sonar-technician`). `cargo test` for the platform-independent modules runs in WSL.
- **Native build and test:** the same desktop, on Windows, from a copy at `C:\dev\sonar-technician`. Run `scripts/sync-to-windows.sh` in WSL to refresh the copy, then build from PowerShell there. The copy is disposable; the WSL repo is the only one with git history. Probe output written there can be read from WSL at `/mnt/c/dev/sonar-technician/`.
- WSL2 can't reach Sonar (Windows loopback) or `coreProps.json`, so anything touching live Sonar runs on Windows.

## Conventions

- Error handling: `thiserror` for library-style errors in `sonar/` and `config`, `anyhow` at the edges (`main`, CLI). No `unwrap()`/`expect()` outside tests and truly impossible cases (leave a comment saying why).
- Logging: `tracing`. `info` for state changes (connected, mode changed, device switched), `debug` for each request, never per-keypress at `info`.
- Keep dependencies lean and verify crate APIs against the version in `Cargo.lock` before using them. Crates like `windows`, `tray-icon` and `ureq`/`reqwest` change their APIs between versions.
- Small, focused commits. Run `cargo fmt`, `cargo clippy -D warnings` and `cargo test` before each commit.
- Commit messages should be short and imperative.

## Working with the user

- Their hardware: a Keychron V1 Max whose knob currently sends F17 = press, F18 = turn left, F19 = turn right (remapped in Keychron Launcher). Sonar's own hotkeys for F17–F19 must be **unbound** in GG while this tool runs, or both will fire. User is willing to further remap keys in Keychron Launcher to support intended functionality. 
- Anything that depends on live Sonar behaviour (shapes, casing, UI sync) must be verified on the user's machine. Ask them to run `sonar-technician probe` or a specific `set` command and paste the output, rather than guessing.
