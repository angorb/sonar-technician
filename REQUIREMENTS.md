# sonar-technician — Requirements

A small, standalone Windows utility, written in Rust, that gives fine-grained keyboard/knob control over SteelSeries GG Sonar: 1% volume steps, hotkeys to pick which channel is being controlled, hotkeys to switch output devices, support for both Classic and Streamer mode, and an on-screen overlay that shows every change.

## 1. Background and problem

- The user's Keychron V1 Max volume knob is remapped (via Keychron Launcher) to send **F17 / F18 / F19** (press, turn left, turn right).
- Sonar's built-in hotkeys move a fader in fixed **5%** steps, with no setting to change that.
- Sonar has no hotkeys for "select which channel the knob controls" or "switch output device".
- Sonar exposes an **undocumented local HTTP API** (used by Sonar's own UI and by community Stream Deck plugins) that accepts arbitrary volume values (0.00–1.00), device redirections and mode changes. This tool drives that API.

## 2. Goals

| # | Goal |
|---|------|
| G1 | Change the volume of the *active channel* in configurable steps (default 1%). |
| G2 | Hotkeys to cycle through channels and to jump straight to a specific channel. |
| G3 | Hotkeys to cycle or set the output device of the active channel (or of all channels). |
| G4 | Work in Sonar **Classic** mode and **Streamer** mode, detecting the mode automatically. |
| G5 | A non-intrusive overlay showing what changed (channel, value, device, mode, mute). |
| G6 | Runs in the background from the system tray, starts with Windows if the user chooses, and survives GG/Sonar restarts. |
| G7 | All bindings and behaviour configurable from a human-editable config file. |

### Non-goals (v1)

- Replacing the Sonar UI (EQ, presets, spatial audio, mic processing).
- macOS/Linux support (Sonar is Windows-only).
- A full settings GUI. Config file plus tray menu is enough for v1.
- Controlling non-Sonar devices or apps.

## 3. Functional requirements

### 3.1 Sonar connection and discovery

- **FR-1.1** Discover the Sonar API base URL at runtime. Never hard-code a port, because it changes every time GG starts.
  1. Read `coreProps.json` from `%ProgramData%\SteelSeries\GG\coreProps.json`, falling back to `%ProgramData%\SteelSeries\SteelSeries Engine 3\coreProps.json`.
  2. Take `ggEncryptedAddress` (for example `127.0.0.1:6327`) and `GET https://{ggEncryptedAddress}/subApps`. The certificate is self-signed and regenerated by GG, so certificate validation **must be disabled for this one request only**, and only for a loopback address.
  3. From the response use `subApps.sonar.metadata.webServerAddress` (plain HTTP, for example `http://127.0.0.1:50453`). Check `subApps.sonar.isEnabled`, `isReady` and `isRunning`, and report a clear status for each.
- **FR-1.2** Cache the base URL. On any connection/transport failure, drop the cache, rediscover, and retry the request **once**.
- **FR-1.3** While GG/Sonar is not running or not ready, poll for it with backoff (for example 2 s, rising to 30 s) without spamming logs, and show "Sonar unavailable" in the tray tooltip and overlay.
- **FR-1.4** Detect the mode with `GET /mode/` (returns a JSON string: `"classic"` or `"stream"`). Cache it for at most 2 s, and refresh it immediately when the API returns the error text `Cannot be called in current mode`.

### 3.2 Channels and active-channel state

- **FR-2.1** Controllable channels: `master`, `game`, `chat` (render), `media`, `aux`, `mic` (capture). Map them internally to whatever token each endpoint needs (see the API notes in CLAUDE.md, where the token differs between volume and redirection routes).
- **FR-2.2** In Streamer mode there are also two **mixes**, `monitoring` (what the user hears) and `streaming` (what goes to the stream). The active target is the pair *(mix, channel)*. A hotkey toggles the active mix.
- **FR-2.3** Actions: `next_channel`, `prev_channel`, `select_channel(<name>)`, `toggle_mix` (Streamer only, and a no-op with an overlay hint in Classic).
- **FR-2.4** The channel cycle order and which channels are included are configurable (for example skip `mic`).
- **FR-2.5** Remember the active channel/mix across restarts.

### 3.3 Volume

- **FR-3.1** `volume_up(step)` / `volume_down(step)` adjust the active target's volume. The default step is 0.01 and the value is clamped to [0, 1].
- **FR-3.2** Round values to 2 decimal places before sending.
- **FR-3.3** **Coalesce rapid input.** A fast knob spin sends many key events. Accumulate them locally, show the new value in the overlay immediately, and send only the latest value to Sonar (latest-wins, at most one request in flight per target). The hotkey thread must never block on HTTP.
- **FR-3.4** Optional acceleration: if more than N steps arrive within T ms, multiply the step (configurable, off by default).
- **FR-3.5** `toggle_mute`, plus `set_volume(<0–100>)` for presets.
- **FR-3.6** The source of truth is Sonar. Read the current value from Sonar on startup, on channel switch, and after a period of inactivity (for example 3 s), so changes made in the Sonar UI are picked up.
- **FR-3.7** The Sonar UI should reflect changes made by this tool. See the open question in §7 on whether REST writes update the GG UI. If they don't, use the documented workaround: in Classic mode, set the Windows endpoint volume of Sonar's virtual device for that channel ("SteelSeries Sonar - Gaming / - Chat / - Media / - Aux / - Microphone"), which Sonar mirrors into its fader. `master` has no virtual device and always goes through REST.

### 3.4 Output devices

- **FR-4.1** List the playback devices Sonar can route to with `GET /audioDevices`, excluding Sonar's own virtual devices (`isVad == true`) and devices with the wrong data flow.
- **FR-4.2** Actions:
  - `next_output_device` / `prev_output_device`: cycle the active channel's output device.
  - `set_output_device(<name pattern>)`: set it to a device matched by name (case-insensitive substring), with the device ID resolved at runtime.
  - Optional `scope = "all"`: apply to every output channel at once (the common "headphones ↔ speakers" switch).
  - Optional configurable **device cycle list**, so cycling only rotates through the user's chosen devices.
- **FR-4.3** Classic mode: `PUT /classicRedirections/{game|chat|media|aux|mic}/deviceId/{id}`.
- **FR-4.4** Streamer mode: change the device of the `monitoring` / `streaming` mix (or `mic`) through `/streamRedirections/...`. The exact PUT route is **unconfirmed** and must be verified (see §7).
- **FR-4.5** After a device switch, wait briefly (about 300–500 ms) and re-apply the channel's volume, because Sonar drops volume/mute changes made while it rebuilds the audio path. Re-send the volume once more after about 1.5 s. Note that Sonar ignores a write equal to its stored value, so re-applying may need a ±0.01 nudge followed by the real value.
- **FR-4.6** Match devices by ID first and by name as a fallback, because IDs change when drivers are reinstalled.

### 3.5 Mode

- **FR-5.1** Detect and display the mode, and update automatically when the user changes it in the Sonar UI.
- **FR-5.2** Optional `toggle_mode` action (`PUT /mode/classic` | `/mode/stream`), disabled by default because switching mode is disruptive.
- **FR-5.3** Every action must behave sensibly in both modes. Where something doesn't apply, show an overlay message ("Mix toggle is only available in Streamer mode") instead of failing silently.

### 3.6 Hotkeys

- **FR-6.1** Global hotkeys that work while other apps, including borderless-fullscreen games, have focus.
- **FR-6.2** Support F13–F24 (the Keychron remap targets) plus normal keys with modifiers (Ctrl/Alt/Shift/Win).
- **FR-6.3** Bindings live in config: a key chord mapped to an action and its arguments. Several chords can map to the same action.
- **FR-6.4** Report hotkeys that fail to register (already taken by another app) once, in the overlay or tray and in the log.
- **FR-6.5** Default bindings for the user's setup:
  - F19 (knob right) → `volume_up` 1%
  - F18 (knob left) → `volume_down` 1%
  - F17 (knob press) → `next_channel`
  - Shift+F17 → `toggle_mute`
  - Ctrl+F17 → `next_output_device` (scope: all)
  - Alt+F17 → `toggle_mix`

  Knob directions confirmed by the user on 2026-11-21: F17 = press, F18 = turn left, F19 = turn right.
- **FR-6.6** Key repeat from a held key should repeat the action.

### 3.7 Overlay

- **FR-7.1** A small borderless, topmost, **click-through**, non-activating window (it must never steal focus or swallow input, and must not appear in Alt-Tab or the taskbar).
- **FR-7.2** It shows:
  - the mode (Classic/Streamer)
  - the mix (Streamer)
  - the channel name
  - a volume bar plus a numeric percentage
  - the mute state
  - the device name on a device switch
  - short error/status messages
- **FR-7.3** It appears on each change, updates in place during rapid changes (no flicker or stacking), and fades out after a configurable timeout (default 1500 ms).
- **FR-7.4** Position (corner plus offset), monitor (primary or the monitor with the cursor), scale, opacity and an on/off switch are configurable.
- **FR-7.5** Respect per-monitor DPI.
- **FR-7.6** Known limitation to document: overlays can't draw over exclusive-fullscreen games. Borderless/windowed works.

### 3.8 Tray and lifecycle

- **FR-8.1** System tray icon. Its tooltip shows the connection status, mode and active channel.
- **FR-8.2** Tray menu items:
  - active channel (submenu)
  - output device (submenu)
  - toggle overlay
  - open config
  - reload config
  - open log folder
  - start with Windows (toggle)
  - quit
- **FR-8.3** Single instance only. A second launch notifies the running one and exits.
- **FR-8.4** No console window in release builds (`windows_subsystem = "windows"`).
- **FR-8.5** "Start with Windows" uses the HKCU `Run` registry key and doesn't require admin.

### 3.9 Configuration

- **FR-9.1** A TOML file at `%APPDATA%\sonar-technician\config.toml`, created with commented defaults on first run.
- **FR-9.2** Hot-reload when the file changes, plus a tray "Reload". An invalid config keeps the previous one and shows the parse error (line and column) in the overlay/log.
- **FR-9.3** Example shape (illustrative only):

```toml
[volume]
step = 0.01
acceleration = { enabled = false, window_ms = 80, threshold = 4, multiplier = 3 }

[channels]
cycle = ["master", "game", "chat", "media", "aux"]

[devices]
cycle = ["Headphones", "Speakers"]   # name substrings; empty = all non-virtual devices

[overlay]
enabled = true
position = "bottom-right"
offset = [24, 24]
timeout_ms = 1500
opacity = 0.9
monitor = "cursor"                   # "primary" | "cursor"

[[bindings]]
keys = "F19"
action = "volume_up"

[[bindings]]
keys = "F18"
action = "volume_down"

[[bindings]]
keys = "F17"
action = "next_channel"

[[bindings]]
keys = "Ctrl+F17"
action = "next_output_device"
scope = "all"
```

### 3.10 Diagnostics

- **FR-10.1** A rolling log file in `%LOCALAPPDATA%\sonar-technician\logs`. The level is configurable and defaults to `info`. Don't log every keypress at `info`.
- **FR-10.2** A CLI subcommand `sonar-technician probe` that runs discovery and dumps the raw responses of every known GET endpoint to a timestamped folder. It's used to confirm JSON shapes and to debug after a GG update.
- **FR-10.3** A CLI subcommand `sonar-technician set <channel> <0-100>` (and similar) for scripting and testing without hotkeys.

## 4. Non-functional requirements

- **NFR-1 Latency.** The overlay reflects a keypress within 16 ms. The new value reaches Sonar within 50 ms when idle.
- **NFR-2 Footprint.** Idle CPU about 0%, RAM under 30 MB, release binary ideally under 10 MB. No polling faster than needed. Hotkeys are event-driven.
- **NFR-3 Robustness.** No panics in normal operation. Every Sonar/HTTP failure is handled and shown, never a crash. Survives GG restarts, sleep/resume, device unplugging and Sonar updates that break an endpoint, where it degrades that feature only.
- **NFR-4 Security.** Talk only to loopback addresses. Disable TLS verification only for the GG discovery call, and only when the host is `127.0.0.1`/`localhost`. No telemetry or network access beyond localhost.
- **NFR-5 Permissions.** Runs as a normal user with no admin rights and no low-level keyboard hook, unless `RegisterHotKey` turns out to be insufficient.
- **NFR-6 Platform.** Windows 10 1809+ and Windows 11, x64.
- **NFR-7 Build.** `cargo build --release` on stable Rust with MSVC produces a single self-contained `.exe`.

## 5. Architecture (suggested)

```
main ─┬─ UI thread (Win32 message loop): hotkeys (RegisterHotKey), tray icon, overlay window
      │        │  Action events
      │        ▼
      ├─ Controller (state machine: mode, active mix/channel, cached volumes, devices, pending writes)
      │        │  commands (latest-wins per target)        ▲ state snapshots → overlay/tray
      │        ▼                                           │
      └─ Sonar worker thread ── SonarClient (discovery, HTTP, retry) ── Sonar local API
                         └──── optional Windows Core Audio endpoint volume writer
```

- `sonar` module: the API client behind a `SonarApi` trait, so the controller can be tested against a fake.
- `controller` module: pure logic with no Win32 or HTTP. This is where most unit tests go.
- `platform` module: hotkeys, tray, overlay, autostart, single-instance, Core Audio.
- `config` module: load, validate, defaults, hot-reload.

## 6. Acceptance criteria

1. With Sonar in Classic mode, one knob detent changes the active channel by exactly 1%, and the Sonar UI agrees (immediately, or after reopening the Sonar window if REST writes turn out not to push to the UI, which must be documented).
2. Spinning the knob quickly from 20% to 80% produces no lag in the overlay, ends at exactly the expected value, and doesn't flood Sonar with requests.
3. F17 (knob press) cycles master → game → chat → media → aux, and the overlay names each one.
4. Ctrl+F17 moves every output channel from headphones to speakers and back, and the volumes are unchanged afterwards.
5. After switching Sonar to Streamer mode in its UI, the tool picks this up within 2 s. Volume and mix toggling then work for both the monitoring and streaming mixes.
6. Killing and restarting GG (new port) makes the tool recover automatically within about 5 s with no user action.
7. The overlay never takes focus from a game or text field, and clicks pass through it.
8. `sonar-technician probe` writes the raw JSON for every GET endpoint.
9. `cargo clippy -- -D warnings` and `cargo test` pass.

## 7. Open questions and risks (resolve in Phase 0)

| # | Question | How to resolve |
|---|----------|----------------|
| Q1 | Exact JSON shapes of `/audioDevices`, `/classicRedirections`, `/streamRedirections`, `/volumeSettings/classic`, `/volumeSettings/streamer`. | `sonar-technician probe` on the user's machine. Save the samples to `docs/api-samples/` and build serde types from them. |
| Q2 | Do REST volume writes update the GG UI live, or only the audio? Reports conflict. | Test manually. If the UI doesn't update, use the Windows-endpoint-volume path for Classic channels (FR-3.7). |
| Q3 | Casing of the master path: `master` vs `Master`. Volume keyword: `Volume` (Classic) vs `volume` (Streamer). Mute keyword: `Mute` (Classic) vs `isMuted` (Streamer). | Try each against the live API and record what works in CLAUDE.md. |
| Q4 | The PUT route for changing the monitoring/streaming/mic **device** in Streamer mode. | Capture Sonar UI traffic with Wireshark/Fiddler on the discovered port while changing the device in the UI. |
| Q5 | The ChatMix route: `/chatMix` vs `/v1/chatMix?balance=`. Not needed for v1, but nice to have. | Probe. |
| Q6 | Does Sonar push state changes (websocket `/sock`, `SONAR_EVENT_VOLUME_DATA`) that the tool could subscribe to instead of polling? | Investigate after v1. Polling is acceptable for v1. |
| Q7 | Does `RegisterHotKey` receive F13–F24 from the Keychron in every app the user cares about, including games? | Test early. Fall back to a `WH_KEYBOARD_LL` hook only if needed. |

**Risk:** the API is unofficial and can change with any GG update. Keep every route string in one module and make failures obvious (overlay message plus a log entry with the URL and status), so fixing an endpoint after an update is a one-line change.
